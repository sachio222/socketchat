# Security

This document says what Socketchat v4.0 protects, what it does not, and how to report a vulnerability. Every claim here matches the code in this repository. If you find one that does not, that is a bug: please report it.

The server never holds a key that can read messages, files, display names, group names or room topics. It does see message sizes rounded up to blocks of 256 bytes, file sizes, timing, IP addresses, each group's list of random member keys, and each group's settings for who can invite, slow mode and who can set the topic. Message contents have post-quantum protection; the connection to the server does not yet.

## Terms

- **End-to-end encryption:** only the people in a chat can read it. The server and anyone watching the network see scrambled data.
- **MLS (Messaging Layer Security):** the internet standard for encrypted group chat, RFC 9420. Each change to a group (someone joins, leaves, or refreshes keys) starts a new **epoch** with new keys.
- **Commit:** an MLS message that changes the group and moves it to the next epoch. A **proposal** is a suggested change that a later Commit applies.
- **Welcome:** an MLS message that lets a new member join a group.
- **KeyPackage:** a public bundle a person publishes so others can add them to a group.
- **Post-quantum:** safe against a future quantum computer. ML-KEM is the United States standard (FIPS 203) for post-quantum key exchange. X25519 is today's common key exchange. A **hybrid** uses both, so it is never weaker than X25519 alone.
- **Identity key:** each person's long-term signing key. Its private half stays on their device. Invite links carry its fingerprint (a SHA-256 hash), and safety numbers are built from it.
- **Room:** a group chat. The protocol calls it a group.
- **Group key:** a fresh signing key a person makes for each group they join.
- **Mailbox:** where the server keeps a member's encrypted messages for one group. Its ID is that member's group key.
- **Safety number:** a 60-digit number built from two people's identity keys. If both screens show the same number, nobody sits in the middle.

## What the server sees

- For each group: the members' group keys, which double as mailbox IDs, the group's admin list, and its settings: whether only admins can invite, how long slow mode holds members between messages, and whether only admins can set the room's topic. The server reads the settings so it can enforce the first two (see below), and it sees the third because it travels with them. They say nothing about what anyone writes; the topic itself travels encrypted.
- Every group change. Commits and proposals travel signed but unencrypted, so the server can check them (see below).
- Each person's server account key, which lets them create groups. Stored records do not connect it to any group.
- The size of every encrypted message, rounded up to a whole number of 256-byte blocks. Apps pad each message with zeros before encrypting it, so every text of up to about 170 characters of English is the same size, and a longer one grows a block at a time. Apps on 0.5.1 and older do not pad, so the server sees the exact length of their messages.
- The timing of every message and file. Padding does not hide when a message is sent.
- The size of every encrypted file, and which mailbox uploaded each file.
- IP addresses of connected apps. An app signs in with all of its keys for a server on one connection, so an operator watching live traffic can link one person's mailboxes through their IP address and connection, even though stored records cannot. An app asks for its list of open invite links on that same connection, and the server keeps no record of the question.
- Which member made the link a waiting join came through, until that join completes. The server then clears it.
- Each connection's protocol version, which tells apps on 0.4.0 (protocol 1), 0.5.0 and 0.5.1 (protocol 2) and 0.5.2 or later (protocol 3) apart.
- How fast each member posts in each room. The server counts each member's posts in memory to limit fast posting, by the mailbox the connection posts with, which it already knows. It keeps no record of the counts on disk.
- When a room ends. Closing a room shows as an admin's Commit that removes everyone else, followed by that admin leaving. When the last member's app, on 0.5.0 or later, leaves while alone in the room, the server deletes everything it holds for that room at once: its log, the Welcomes waiting for its mailboxes, its mailboxes, invite links, join requests, files, a hash of each group key that left it, and MLS state. Its hourly sweep also deletes rooms with no members. The votes to close travel encrypted, so the server never sees them.

Stored rows also carry creation times. Someone holding the server database can sometimes guess a link from times alone, for example an account and a mailbox registered in the same second when a new person joins with a group invite.

## What the server never sees

- Message text, file contents, display names, group names, room topics.
- Any key that can decrypt messages or files.
- Any identity key or safety number. The voucher an inviter sends with a Welcome holds the inviter's identity key, and it travels sealed for the joiner under a key the server does not have.
- The secret part of an invite link. It sits after the `#`, which apps never send to the server.

## Why the server knows group membership

The server delivers each encrypted message to the mailboxes in a group, so it has to know which mailboxes those are. It also checks every Commit before anyone sees it: the signature, the epoch, and that the sender may make that change. Removing someone else, changing the admin list and changing the room's settings need an admin, and so does adding someone to a room that lets only admins invite, or to any room on a server whose operator lets only admins invite. Those checks stop a non-admin's change and two changes racing for one epoch. The server also refuses a member's invite link in an admins-only room, and a link whose maker can no longer invite when someone uses it; holds members who are not admins to the room's slow mode; and limits how fast each member posts, admins at ten times a member's pace. Over a limit it refuses the post with a wait and never removes anyone. Removals are never held up, and each member may ask to leave once per epoch, at the size apps send. Apps encrypt nothing for a room while it holds them back, so a refused post never puts a member's keys out of step with the others, and a held message goes only to the people who were in the room when it was typed. When someone leaves a room or is removed, the server deletes the invite links they made there, any join it recorded as waiting on one of those links, and any Welcome nobody fetched for them or for those joins. It also refuses their old group key for as long as the room exists.

The server cannot check the encrypted parts of a Commit, the new keys it hands each member. A buggy or hostile app can still send a Commit that passes the server's checks but that some members cannot apply. Those members fall out of step: they stop being able to read the group. Their app says so ("The chat Book club fell out of step. Ask an admin to remove you and invite you again.") instead of going quiet, and an admin can remove them and invite them again.

Apps also check each change themselves. An app applies a Commit or proposal only when a member of the room signed it, and refuses one from anyone outside the room, the server included. The room stays as it was, and the app says so ("The chat Book club got a change from someone who is not a member. Socketchat refused it."). Apps also apply the server's rules on who may make a change: removing someone else, changing the admin list or changing the room's settings needs an admin, adding someone needs an admin while the room lets only admins invite, a member may only propose to leave, and when the last admin leaves, the new admin must not be someone the checking app saw join after itself, and the room's settings must stay as they were. Each rule reads the room as it stood before the change, so a change from someone who was removed first, or who was not an admin then, does not count. A change that breaks these rules is refused the same way ("The chat Book club got a change from a member who had no right to make it. Socketchat refused it."). Room settings travel inside these signed changes, so neither the server nor a member who is not an admin can forge or flip one. A server from before 0.5.2 does not know room settings and cannot keep them, so apps on 0.5.2 refuse to set them there, and `/settings` and `/details` say the server cannot enforce them. The member list an app shows comes from the room's MLS state, so everyone in the room shows there, by a short form of their key when the app has no name for them.

An app takes each encrypted message as its sender's only when the key MLS checked it against, from the epoch it was written in, is the key of the member who holds that place in the room now. A message therefore always shows under the member who wrote it.

A room's topic travels the way its name does, inside an encrypted message, so the server never sees it. The setting for who may set it, admins only or anyone in the room, is a room setting like the others, and the server sees it. Every app judges a topic by the room at the point it arrives: the sender must still be in the room and be an admin, or any member while the room lets anyone set the topic. A topic from anyone else, or from a member removed before it arrived, changes nothing. Each topic carries a signature by the group key of the member who set it, over the room, the time and the text. When an admin's app passes the topic on to someone who joins, the newcomer checks that signature, so the app that passes it on cannot change the text or name someone else as its setter, and a topic passed on only fills in a missing one, never replaces a newer one. A topic counts toward the posting pace like any message, and nothing is encrypted for it while the room holds the member back. Leaving, `/clear`, `/forget` and a room's ending delete its topic from the computer.

Socketchat limits what that knowledge reveals. Group keys and mailboxes are per group, so the database shows separate groups of random keys. Names, group names and identity keys travel only inside encrypted messages or the sealed voucher. Retention is short and set by the operator. The server database overwrites deleted rows and cleared fields with zeros (SQLite's `secure_delete`), so expired messages and the name of a used invite's maker do not linger in free pages. The server also empties SQLite's write-ahead log after it deletes a room or a member's rows. On macOS and Linux it keeps its data directory for its own account (0700 for folders, 0600 for files, the certificate and its key included), and narrows one an earlier release made when it starts. Hiding membership from the server completely is the first item in [ROADMAP.md](ROADMAP.md).

## What stays on your computer

Socketchat keeps its data in one encrypted profile on your computer (see "Local data" under "Cryptography").

- **Rooms you are in** keep their messages, files list, member list and keys there.
- **When you leave a room, are removed from it or it closes,** Socketchat deletes its keys and MLS state, with its member list, files list and your record of invite links into it. After your own leave this happens at once. After a removal or a close it happens as soon as your app learns of it, which for an app that was not running is its next sync with the server. The room's messages and add-on messages go once you have read them:
  - When you leave with everything read, they go at once. The chat screen first shows any messages you have not read and asks you to type `/leave` again.
  - When you were removed or the room closed, they go when you open another room or quit Socketchat.
  - A room with messages you have not read keeps its messages until you read them. Once 30 days have passed since the room ended, Socketchat deletes them, read or not, the next time it opens, you open another room, or it or one of its commands finishes. The names of the people who wrote those messages stay with them until they go.
- **`/clear`** deletes a room's messages and its files list from your computer while you stay in it. Files shared there before then can no longer be saved with `/save`.
- **Spare join keys.** A join request carries one KeyPackage for each kind of encryption Socketchat allows (see "Cryptography"). For a join request made with 0.5.0, Socketchat deletes the ones the join did not use, with their private keys, once you join. A request lodged with 0.4.0 keeps its spare keys.
- **Deleted rows are overwritten** inside the encrypted file (SQLite's `secure_delete`). Socketchat then clears old copies of them out of the profile's log file (SQLite's write-ahead log). If the profile is busy at that moment, old copies can stay in that log file until a later tidy-up, and the app warns when that happens.
- **Files you saved** stay where you saved them. On macOS and Linux, only your account can read a file Socketchat saved.
- **Rooms you left with 0.4.0** lose their history when 0.5.0 first opens the profile.

## Cryptography

- **Group encryption:** MLS (RFC 9420) through OpenMLS 0.9.1, a Rust implementation that SRLabs audited in 2026.
- **Default suite:** `MLS_128_MLKEM768X25519_AES128GCM_SHA256_Ed25519` (0x004F). It uses the hybrid ML-KEM-768 + X25519 key exchange, so recorded traffic stays confidential even against a future quantum computer.
- **Draft status:** suite 0x004F comes from an IETF draft that is not final, and it may change before publication. The suite choice lives in one file, `crates/socketchat-core/src/suite.rs`, so groups can move to the final suite later.
- **Provider:** openmls_rust_crypto 0.6.0 with OpenMLS's `draft-ietf-mls-pq-ciphersuites` feature, which uses an experimental HPKE path in hpke-rs. The 2026 SRLabs audit covered the OpenMLS core. It did not cover this experimental post-quantum path.
- **Fallback suite:** the standard `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (0x0001), which has no post-quantum protection. A server operator can require it with `require_standard_suite = true`; the server then refuses new groups on any other suite. Groups that already exist keep their suite.
- **Signatures:** Ed25519 everywhere, which is not post-quantum. Forging one would take a quantum computer at the moment of the attack. Every Socketchat signature outside MLS covers a context string first, so a signature made for one purpose never verifies for another.
- **Connection:** TLS 1.3 through rustls 0.23.45 with the ring crypto provider. Its key exchange is classical X25519, so the connection layer is not post-quantum, while message contents inside it are. Someone who records traffic today and later breaks X25519 would learn what the server itself sees, but not message or file contents. The server makes a self-signed certificate at `init`. Invite links carry its SHA-256 fingerprint and apps pin it, so no certificate authority is involved. A link with a different fingerprint for a server already in use changes nothing until the person accepts it, and the new pin takes effect only after a connection under it works.
- **Files:** XChaCha20-Poly1305 in the STREAM construction, in 64 KiB chunks, with a fresh random key per file. STREAM catches chunks that were changed, dropped or reordered. The file key, name and SHA-256 hash travel inside an encrypted MLS message, and the receiving app checks the hash before saving.
- **Invites:** the joiner signs their request, meaning the token and their new mailbox key, with an Ed25519 key whose seed comes from the invite secret through HKDF-SHA256, and sends the signature inside their KeyPackage. A server without the link cannot slip in its own KeyPackage. Other members hold only that key's public half, so they can check a request but cannot make one. The inviter also signs a voucher with their identity key, which the joiner checks against the fingerprint in the link. The joiner's app marks the join verified only after the group key the voucher names posts a profile inside the group, bound to the identity that signed the voucher. Until then the app says it is waiting for the inviter to confirm the invite, and it keeps the person's display name, identity key and app version out of the room; it shares them once the join is confirmed or the person marks someone in the room verified. The inviter's app posts its profile after every add, so this happens on its own. Other members get the voucher, the public key and a seal key derived from the secret, never the secret itself, so any admin can check and complete a join. Apps complete a join only while the member who made the link is still in the room, and never add back a key from the room's admin list. A member's app accepts a voucher only from the inviter it names, signed by the identity that member proved in the group. The inviter's app marks the new member verified only after the joiner proves, with a second key derived from the secret, that they hold the link itself; no other member can make that proof. It accepts one proof per link, and only from the key that joined with that link. The voucher reaches the joiner sealed with XChaCha20-Poly1305 under a key derived from the invite secret with HKDF-SHA256, so the server stores and forwards it without being able to read it.
- **Local data:** one SQLite file encrypted with SQLCipher, keyed by Argon2id from your passphrase. New profiles use 64 MiB of memory, 3 passes and 4 lanes (the second option RFC 9106 recommends), which a Raspberry Pi Zero 2 W should still open in under about 2 seconds. Profiles made before 0.5.1 keep 19 MiB and 2 passes, the OWASP minimum. The salt sits beside the file with the Argon2id settings the profile was made with, so a release can raise the settings for new profiles without locking anyone out. A salt file that asks for more than 256 MiB of memory, 16 passes or 8 lanes is refused as damaged before any hashing starts, so a changed file cannot hang the app or run a 512 MB device such as a Raspberry Pi Zero 2 W out of memory. Only one app at a time can open a profile; a second one gets "Socketchat is already open on this profile." On macOS and Linux the profile folder is for your account only (0700, its files 0600). When Socketchat opens a looser folder or file, it narrows it and says what it changed; on a drive that cannot store these settings, such as a FAT or exFAT drive, it warns instead. It will not open a profile folder that another account owns, and it checks a folder reached through a link where the link points. Socketchat never makes a profile with an empty passphrase, from the prompt or from `SOCKETCHAT_PASSPHRASE`. A profile an earlier release made with an empty passphrase still opens, and Socketchat warns each time that it has no passphrase, since anyone who copies its folder can read it.
- **Key refresh:** MLS changes encryption keys with every group change. Each app also refreshes its own keys in a group when they are more than a week old, so a stolen encryption key stops unlocking new messages.
- **Randomness:** the operating system's random source, through the libraries above.

## What leaves your computer besides chat

Apart from the servers you join, Socketchat contacts one place: GitHub, to learn whether a newer release is out. It never sends anything to socketchat.org.

- **When.** At most once a day, when the chat screen opens or when a command that opens your profile runs, such as `socketchat sync`.
- **What it sends.** One HTTPS request to api.github.com for the latest release of sachio222/socketchat, with `socketchat` as its user agent and no cookie or token. It carries nothing about you, your profile, your servers or your chats. GitHub sees your IP address and the time, as it does for any web request. Socketchat checks GitHub's certificate against the certificate authorities your system trusts.
- **What it does with the answer.** When the release GitHub names is newer than yours, the chat screen's bottom line and the output of commands such as `socketchat sync` say "Socketchat 0.5.3 is out. Run socketchat update." A copy that Homebrew installed says "Run brew upgrade socketchat." instead. The check downloads and installs nothing, and so does `socketchat update`, which only prints the command that installs the new version (see "Checking a release"). A check that fails says nothing, and the next one comes a day later.
- **Turning it off.** Type `/updates off` in the chat screen, and your profile keeps the setting. Or set the environment variable `SOCKETCHAT_NO_UPDATE_CHECK` to `1` (any value but empty or `0` works). While the check is off, Socketchat makes no request to GitHub at all. `/about` says whether the check is on and when GitHub last answered, and `/updates on` turns it back on.

## What the app shows and runs

Text from other people, and from links they send, reaches your terminal. Socketchat keeps that text from passing itself off as something else.

- **Names and messages.** Socketchat removes terminal control characters and direction controls from names, room names and messages before it shows them, and invisible characters from names too, so two different names cannot look the same. In the output of `socketchat log` and `socketchat sync`, the second and later lines of a message are indented, so a line at the left edge always starts a new message and names who wrote it.
- **Room topics.** A topic is one line from a room's admins, or from anyone in a room whose admins allow it, so it gets the strict filter that names get: no control characters or escape codes, so a topic cannot move the cursor, recolor the screen, set the terminal's title or ring its bell; no direction controls or isolates; no invisible characters or Hangul fillers. Line breaks and other runs of whitespace become one space, and the topic stops at 300 characters. The setter's app refuses a longer one, and every other app cuts it. Every place a topic shows, the line under the room's name, the room's notices, `/topic`, `/details` and `socketchat topic`, starts it with `Topic:` and draws it in the topic's own color, never the color of the app's notices, warnings or verified mark, so a topic such as "✓ verified: safety numbers match" cannot pass for the app's own words. The line that says who set it gives their verified state in words. A topic is plain text, so a link in it shows as its full address.
- **Questions.** A question on the chat screen, such as whether to trust a server's new certificate, to mark someone verified, or to send a video or a photo Socketchat cannot clean, takes y only as the first key pressed. Any other key answers no, and a key or click read before the question showed never answers it.
- **Pastes.** On macOS and Linux, in a terminal that marks pastes (bracketed paste), a paste goes into the message box as text and nothing is sent or run until you press Enter. A command runs only when it is one line at the start of the message box, with single spaces between its words, and a command too long for the box shows its start and its end. On Windows a paste still arrives as typed keys.
- **Server addresses in invite links.** Socketchat accepts an invite link only when its server address is an IP address or a host name in plain ASCII letters, digits, hyphens and underscores, and it checks this before it stores anything. A name in another script must be written in its `xn--` form, so a link cannot spell one server's name with look-alike letters from another alphabet.

## Checking a release

- **Build attestations.** From 0.5.1 on, every file in a release has a GitHub build attestation: a signed record of the commit and the release workflow that built it. `gh attestation verify <file> --owner sachio222 --cert-identity-regex '^https://github\.com/sachio222/socketchat(_v4)?/\.github/workflows/release\.yml@refs/tags/v'` checks a file you downloaded.
- **No test-only code.** The `socketchat` program in a release is built from its own package alone, so the code that only the tests use stays out, and the release workflow checks each program for the marker that code carries before it publishes anything.
- **Pinned builds.** Release builds use the exact library versions in `Cargo.lock` and the Rust version named in `rust-toolchain.toml`. The workflows pin each GitHub Action to an exact commit. Only the final hosting job, which attests and publishes the release, can write to the repository; the build jobs get a read-only token. The job that publishes the Homebrew formula reads this repository only, and a token for the Homebrew tap repository alone reaches just the step that pushes the formula there.
- **Updating.** `socketchat update` installs nothing. It prints the command for the way your copy was installed: `brew upgrade socketchat` for Homebrew, the install command again for the installer, or all of them when it cannot tell. On macOS and Linux the install command checks the archive it downloads against a SHA-256 checksum written into the installer, which comes from the same release; it skips the check, saying so, on a computer without the `sha256sum` command. The Windows install command checks no checksum. A checksum from the same release catches a damaged download but not a release someone else published, and the install command never checks build attestations. To check a release's build attestation yourself, run `gh attestation verify <file> --owner sachio222 --cert-identity-regex '^https://github\.com/sachio222/socketchat(_v4)?/\.github/workflows/release\.yml@refs/tags/v'` on each file you downloaded. `brew upgrade socketchat` checks each archive against the SHA-256 checksum in the Homebrew formula.

## What Socketchat does not protect

- **Metadata.** The server sees message sizes rounded up to 256-byte blocks, file sizes, timing, IP addresses and each group's list of random keys, as described above.
- **What happens after delivery.** Receivers can save, copy, screenshot or forward anything you send. Deleting messages or a file removes your copy only.
- **Other people's copies of a room.** Deletion happens in each person's own app. A member on 0.4.0, or a changed app, keeps its copy of the history, and anyone can copy or photograph a screen.
- **One admin acting alone.** The server and apps check admin rights, not votes. One admin can remove every other member, one by one or at once with a changed app, then leave, which deletes the room from the server. Closing only once the admins agree is a rule inside standard Socketchat apps.
- **What add-ons send.** Messages from add-ons and other programs are end-to-end encrypted like text. Socketchat checks only their namespace and kind, stores them, and shows their summary line when they carry one. What the rest of a message says, and what an add-on does with it, is up to that add-on.
- **Location data in videos and some photos.** Socketchat removes location and device data from JPEG, PNG, WebP and GIF images, thumbnails and added second images included. A JPEG keeps only its orientation, the way the phone was turned. It cannot remove them from videos, from other photo formats such as HEIC, TIFF and camera raw files, or from a photo over 100 MiB or one it cannot read, and asks before sending one of those. See [docs/files-photos-videos.md](docs/files-photos-videos.md).
- **An unlocked device.** If someone gets your computer while Socketchat is open, or learns your passphrase, they get your identity key and your messages. Do not put `SOCKETCHAT_PASSPHRASE` in a shell profile on a shared machine.
- **A stolen identity key.** Whoever holds it can pose as you. The identity key never decrypts messages. v4.0 has no command to replace an identity key. If yours is exposed, ask an admin to remove you, set up a fresh profile, join again through new invites, and compare safety numbers with your contacts again.
- **A dishonest server's availability.** A server can delay, drop or refuse messages. It cannot read them, and MLS detects any change to their contents.
- **Idle and slow connections.** The server closes a connection that does not finish its TLS handshake within 10 seconds and say hello within 10 seconds after that, has not signed in within 60 seconds of connecting, or sends nothing for 5 minutes. Until a connection signs in it may send only small frames, 8,192 bytes by default, and past the first 1,024 bytes of each connection, all such connections together hold at most 8 MB of partly sent frames unless the operator sets other limits. A connection may have at most 2 MiB of replies and pushes waiting; the server closes it when a push would go over, and when a write makes no progress for 30 seconds, so a client that stops reading cannot hold memory or a connection slot. One address can hold at most 256 connections unless the operator sets `max_per_ip` lower or higher; the default is high because a whole office or school can share one address. The server answers each connection past that limit with a short refusal the app shows, and while 64 refusals are under way it drops further ones before TLS, so turning people away stays cheap. Apps reconnect and catch up on their own. With the default settings each account can make 5 server invite links every two days, and the room links it makes can register at most 100 new accounts in that time, so one account cannot fill a server with new accounts.
- **Disk space.** The server limits what one room, one member of a room and the whole server keep on disk, by default 200 MB of messages and 4,000 MB of files per room, 4,000 MB of files per member and 8,000 MB in all, of which files may use nine tenths. At a limit it refuses new messages and files with a reason the app shows, until members fetch older ones or they expire. A change that only takes people out of a room, at the size apps send it, still goes through, up to a tenth past the room's limit.
- **Unverified joins.** When an invite check fails, the app shows a red warning. A join whose inviter has not confirmed it yet shows no verified mark. A verified mark comes from the invite link or from comparing safety numbers with `/verify`; a matching display name proves nothing.

## Known advisories

The project checks dependencies with `cargo deny check` on every change. Its `deny.toml` lists the advisories it ignores and why.

- **RUSTSEC-2026-0285 (rustls):** applies to Socketchat. Fixed by pinning rustls 0.23.45.
- **RUSTSEC-2026-0346 to RUSTSEC-2026-0349 (rustls):** fixed only in rustls 0.23.46. That release is under 30 days old, the project's minimum age for a dependency, so the upgrade waits until 2026-11-13. None applies to Socketchat today:
  - 0346 needs a custom client session store that prints session values; Socketchat has none.
  - 0347 needs Encrypted Client Hello, which Socketchat does not use.
  - 0348 needs rustls's brotli feature, which is off.
  - 0349 is a downgrade of a hybrid TLS key exchange; Socketchat's TLS uses classical key exchange only.
- **RUSTSEC-2026-0173 (proc-macro-error2, unmaintained):** a macro crate that runs only at build time, under hpke-rs. It does not run in Socketchat, and no maintained replacement exists upstream yet.

## Reporting a vulnerability

Report security problems privately through GitHub's private vulnerability reporting on https://github.com/sachio222/socketchat: open the Security tab and choose "Report a vulnerability". Do not open a public issue for a security problem. Say what you found, how to reproduce it, and which version or commit you tested.
