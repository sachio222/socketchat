# Architecture

This document explains how Socketchat v4.0's code fits together, for people who want to change it. Read it with [protocol.md](protocol.md), which describes the bytes on the wire, and [SECURITY.md](../SECURITY.md), which says what each part protects.

A relay server keeps an ordered log of MLS messages for each group and checks every group change it can read. Clients hold every key that decrypts anything.

## Terms

- **MLS (Messaging Layer Security):** the IETF standard for encrypted group chat, RFC 9420. Socketchat uses the OpenMLS library.
- **Epoch:** a numbered version of a group's state. Every change to the group starts a new epoch with new keys.
- **Commit:** an MLS message that changes the group and moves it to the next epoch. **Proposal:** a suggested change that a later Commit applies.
- **Welcome:** an MLS message that lets a new member join.
- **KeyPackage:** a public bundle a person publishes so others can add them to a group.
- **PublicMessage / PrivateMessage:** MLS's two wire formats. A PublicMessage is signed but readable; a PrivateMessage is encrypted.
- **GroupContext extension:** extra data in a group's shared state that every member agrees on through MLS.
- **PublicGroup:** OpenMLS's view of a group from the outside: members, their public keys and the GroupContext, with no secret that decrypts anything.

## Crates

| Crate | Job |
|---|---|
| `socketchat-proto` | Frames, the request, response and push enums, and invite links. No cryptography and no I/O, so client and server agree on bytes and nothing else. |
| `socketchat-core` | The client engine with no screen. Holds keys, runs MLS groups through OpenMLS, makes and redeems invites, encrypts files, keeps local storage, and talks to servers. The server also uses its `keys` and `suite` modules. |
| `socketchat-server` | The relay. One task per connection, one SQLite database, and an hourly cleanup task. |
| `socketchat-tui` | The terminal chat screen, built with ratatui and crossterm, on top of `socketchat-core`. |
| `socketchat-testkit` | `TestServer` and `TestClient` helpers, and the integration tests that need a real server. It exists because `socketchat-server` depends on `socketchat-core`, so core's own tests cannot start a server. |
| `socketchat` | The binary. `socketchat` opens the chat screen, `socketchat server ...` runs the relay, `socketchat join <link>` redeems a link, `socketchat invites` lists and cancels open invite links, `socketchat servers` lists the servers a profile knows and forgets one, and `new`, `invite`, `send`, `log` and `sync` serve scripts. |

## The client engine

`socketchat_core::client::Client` is the whole client without a screen. Tests drive several at once against one server, and the terminal app is one front end on top.

- **Opening.** `Client::create_profile` makes a profile with an identity key and a display name; `Client::open` unlocks an existing one with the passphrase. Opening also finishes any room ending that stopped part way, deletes the history of rooms left with 0.4.0, and runs `purge_read` (see "Rooms that end").
- **Acting.** Methods such as `join`, `create_group`, `invite`, `send_text`, `send_file`, `save_file`, `dm`, `remove_member`, `make_admin`, `leave` and `set_display_name` each do one thing and return when the server has answered. Rooms add `rename_room` (admins only), `details` (admins, size, creation and join times, mute state and any request to close), `vote_close` and `close_state` (see "Closing a room"), and calls that send nothing: `mark_seen`, `mark_seen_upto`, `set_muted` and `clear_history`. `lines_to_read` gives the lines a script reads next: the newest ones, or the oldest unread ones when more are unread than it asks for. `invites` lists this person's open invite links on every server and `cancel_invite` stops one. `send_extension` sends a message for an add-on or another program, and `extensions` reads a room's stored ones after a sequence number, at most 500 at a time. `servers` (in `client/servers.rs`) lists the servers a profile knows with the state of each, `forget_server` deletes one from the profile with its rooms and everything kept for them without telling the server, and `new_room_server` says where `create_group` puts a new room: on the open room's server, or else on the newest one where this person has an account. `create_group_at` makes a room on a server the caller picks, as `socketchat new --server` does.
- **Receiving.** `sync` fetches everything new from every server, applies it, and queues events. `take_events` hands them over, oldest first: `Joined` (with whether the join was verified, or waits for the inviter to confirm it), `InviteConfirmed` (the inviter confirmed a join that waited), `JoinRequestHandled`, `Message`, `MembersChanged`, `GroupRenamed`, `NameChanged`, `Left { group, name }` (with the room's name, since its record may already be gone), `FileOffered`, `Extension` (a stored message for an add-on), `CloseVote` (an admin voted on closing a room), `Closed` (a room was closed, and by whom; `Left` follows), `Warning`, `Disconnected` and `Reconnected`.
- **Connecting.** Each connection says Hello with protocol 2. When the server answers `VersionMismatch` naming protocol 1, the client connects once more with 1. `Conn::protocol` gives the version agreed, and `Client::protocol_for` gives it for a room's server. A request newer than the connection's version fails in the app with `NetError::Unsupported` without reaching the server; it does not count as a lost connection.
- **Waiting.** `wait(max)` returns when a server pushes something, a connection drops, or time runs out. It only listens, so it is safe to cancel. The chat screen waits inside `select!` alongside key presses, then calls `sync` outside it, so an MLS step never stops halfway.

The chat screen (`socketchat-tui`) reads keys, pastes and mouse events on a thread of their own and stamps each with the time it was read (`Input` in `run.rs`). A question box (`Modal::is_question`) takes y only as the first key, and a key or click read before the box first showed is dropped. Bracketed paste brings a paste in as one event, which `App::handle_paste` puts into the message box as text; a command runs only from one line at the start of the box, with single spaces between its words. The message box is measured in the clusters and cell widths ratatui draws (`drawn_clusters` in `ui.rs`), so a command's end always shows. The screen wraps only the messages that can reach the window. Mouse capture follows `/mouse`, and colors come from `theme.rs`: phosphor unless `/theme classic` is saved in the profile or `SOCKETCHAT_THEME` overrides it for one run. A panic in the screen's own task gives the terminal back before its message prints.

During `sync` the client also refreshes its own keys in any group where they are more than a week old (`KEY_REFRESH_SECS`), and repeats its profile, and the group's name and kind, in groups where someone new joined, since a newcomer cannot read older messages. It fetches each group's log until the server sends an empty page, or a page that does not move past where it started. It reads waiting join requests a page at a time, each page starting after the last request of the one before, until a page comes back empty, and tries each request once per sync. A dropped connection shows as `Event::Disconnected` and the next sync reconnects; a problem in one group, or with one join request, becomes an `Event::Warning` and sync carries on with the rest. When a Commit from someone else, or any message from a later epoch, will not apply, the client warns once that the chat fell out of step.

What travels inside encrypted application messages is the `AppMsg` enum in `appmsg.rs`: text, a member's profile (display name plus the identity key's signature over their group key), the group name, invite vouchers, a joiner's proof that they hold an invite link, file offers, the steps for opening a direct message, messages for add-ons and other programs, the app version each member runs, admins' votes on closing a room, and the room's topic, signed by whoever set it. [protocol.md](protocol.md) lists every variant and the rules for adding one. All text from other people passes through `sanitize.rs`. Names lose terminal control characters, direction controls and invisible characters (Unicode format characters and Hangul fillers), so two different names cannot look the same. A room topic gets the same filter (`clean_topic`), with line breaks folded to spaces and a cap of 300 characters. Message text loses only control characters other than the newline, and direction controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069). Joiners and tag characters stay, so emoji sequences such as a family, subdivision flags such as Scotland's, and scripts that need a zero-width non-joiner, such as Persian, arrive intact. Both are capped in length. The server's own refusal and error text goes through the message-text filter too.

## Keys

Every key is Ed25519. Each person holds:

- an **identity key**, one per person, which stays on their device. Invite links carry its fingerprint and safety numbers are built from it. Its public half never reaches the server in readable form: it travels inside the group's encrypted messages and inside the voucher sealed for a joiner (see "Invites");
- a **group key** for every group they join. It is their MLS credential in that group, and the group's mailbox on the server belongs to it. A `Binding`, signed by the identity key, ties the two together inside the group's encrypted messages;
- a **server account key**, one per server, which lets them create groups.

A connection signs in by signing a random challenge with each key it uses. The server never records which account created which group or mailbox.

## The server's checks on group changes

The server loads each group as an OpenMLS `PublicGroup` (in `groups.rs`) and checks every message before it enters the log:

- **Wire format.** Commits and Proposals must be PublicMessages, so the server can read and check them. Application messages must be PrivateMessages from a current member, for the current epoch or one of the two before it.
- **Admin list.** The admins' group keys live in a GroupContext extension with type `0xff00`, from the private-use range of RFC 9420. Each entry is a 2-byte length (always 32) followed by the key. Anything malformed reads as no admins, which means "refuse".
- **Who may do what.** Adding someone needs an admin, or any member when the server allows members to invite. Removing someone else, or changing the admin list, needs an admin. Anyone may remove themselves. A member may only propose their own removal; other proposals are refused. Other proposal kinds, such as ReInit, are refused. When someone leaves or is removed, the server deletes the invite links they made in that room, with any join still waiting on one of them and that joiner's mailbox, and keeps a SHA-256 hash of their group key in `retired_keys` so the key cannot register again while the room exists. Apps check the same rules before they merge a Commit or store a proposal (`commit_allowed` in `client.rs`), and refuse one that breaks them with a warning, leaving the room at its epoch. Before that, `apply_entry` refuses any Commit or proposal whose sender is not a member of the room, the same way. They accept an add from any member, since an app cannot see whether the server allows members to invite. When an app commits leaves, it includes only members' requests to leave and its own admin change.
- **Admins never run out.** After a change at least one admin must remain. If the last admin leaves, that Commit must make the longest-standing remaining member the only admin, and the server refuses it otherwise. Each app also picks and checks that member against its own `members.joined_seq`, which records the log position of every add it saw: a member it saw join after itself is never accepted, and among members already in the room when it joined, the server's order decides.
- **Adds match invites.** Someone can only be added if their mailbox redeemed an invite to this group.
- **Epoch ordering.** The server accepts a Commit for epoch N only while the group sits at epoch N. The first valid Commit wins and gets the next sequence number. A Commit for any other epoch gets `Conflict { epoch }`; that client fetches what it missed and tries again. If a reply is lost on the way, the Commit stays staged in OpenMLS's storage, so it survives a restart. Before its next change or message in that group, the client reads the log to the end: OpenMLS recognizes its own Commit (`OwnPendingCommit`) and the client merges it, records who it added and removed, and repeats its profile and the group's name for anyone it added; a different Commit for that epoch replaces it; and a log that ends without it means the server never took it, so the client drops it.

  When the post times out instead, the server may still be working on it. The client closes that connection and keeps the Commit staged through one more sync round, even if the log ends without it, and makes no new Commit in that group until it is settled. One window stays open. If the server takes the Commit only after that round, the client has already dropped it, cannot apply what follows, and says the chat fell out of step. An admin then removes the member and invites them again.

New groups get one check of their own: the group must hold only its creator, as its only admin, with a mailbox registered for that purpose, on an allowed suite.

## Per-group keys and mailboxes

Every time a person joins or creates a group, their app makes a fresh group key and registers it as a new mailbox. The server's database therefore shows each group as a separate set of random keys. A direct message started with `/dm` inside a shared group exchanges the new chat's KeyPackages and token through that group's encrypted messages, so the server sees two unrelated groups. The request carries the asker's key in the new chat; the other app counts the chat as verified only when the Welcome comes from that key, for that chat, and the asker's identity is already verified.

## Invites

An invite link holds the server address, a token the server stores, and, after the `#`, the server certificate's fingerprint. A group invite adds the inviter's identity fingerprint and a random invite secret. Apps never send the part after `#` to the server.

1. The inviter's app asks the server for a token, then signs a **voucher** with its identity key: the token, a SHA-256 hash of the secret, the group ID, the inviter's group key and an expiry. It sends the group the voucher, the public half of the request key, and the seal key, inside an encrypted message, so any admin can complete the join. Both keys come from the secret with HKDF-SHA256: the request key is an Ed25519 key whose seed is derived with info `socketchat/v1/invite-sign` (`invite_signing_key` in `keys.rs`), and the seal key is `voucher_seal_key`. The secret itself stays with the inviter and the link. A member's app keeps a voucher only when its sender is the inviter it names, with the identity that sender proved in their profile, and a later voucher for the same token never replaces it.
2. The joiner's app pins the server certificate, makes a fresh group key, registers a mailbox with the token, and lodges a KeyPackage for each allowed suite. Each KeyPackage carries, in a KeyPackage extension of type `0xff01`, an Ed25519 signature over the token and the new mailbox key, made with the request key it derives from the secret (`sign_join_request` in `keys.rs`). The KeyPackage's own signature, by the mailbox key, covers that extension, and the bundle stays the plain list of KeyPackages the server checks.
3. The server pushes the join request to the group's online members. The inviter's app, or any admin's, checks the signature against the public key from the voucher message (`join_request_ok`), adds the KeyPackage that matches the group's suite with a Commit, and posts the Welcome with the voucher. The voucher travels beside the Welcome sealed under the seal key (`seal_voucher` in `keys.rs`), so the server stores and forwards it without seeing the inviter's identity key.
4. The joiner's app opens the voucher with the seal key it derives from the link's secret, then checks its signature against the fingerprint in the link, its token, secret and group, that the member who added them is the voucher's inviter or an admin, and that the inviter's group key is in the group. Anything else shows a red warning. The join then waits for the inviter: it counts as verified once the inviter's group key posts a `Profile` in the group whose binding is signed by the voucher's identity (`awaited_inviters` in the store holds what it waits for). The app reads the new room's log before it reports `Joined`, so a profile the inviter already posted, as their app does after every add, makes the join verified at once; a later one raises `InviteConfirmed`. If the inviter leaves first, the join becomes unverified with a warning. A voucher past its expiry, with every other check passing, also leads to that wait: a lodged request can wait 7 days, longer than the link's 24 hours.
5. The joiner's app posts an `InviteProof`: an HMAC over the group ID and its new group key, under a third key derived from the secret (`invite_proof` in `keys.rs`). Only the inviter's app can check it, and other members cannot make it from the keys they hold, so the inviter's app marks the newcomer verified only on a good proof. It records which key joined with each of its links, from its own add or from the signed request inside the KeyPackage of someone else's add, accepts a proof only from that key, and then forgets the link's secret, so a link verifies one person once. The app stores the proof before posting it and posts any proof it still owes on each sync, so a connection that drops right after the Welcome does not lose it; its profile is owed the same way. The joiner's profile and app version stay out of the room (`held_profiles` in the store) until the join is confirmed or the person marks someone in the room verified, and until then the app makes no invite links and starts or accepts no direct messages from that room. A direct message asked for inside a shared room and completed by the member who asked is not held, since that member already has the profile from the shared room.

Members hold only the request key's public half, so they can check a request but cannot make one: a member cannot bring someone in through another person's link, even where only admins may invite. A request that fails the check is ignored, with one warning per request each session.

A link that names a server this profile already uses, with a different certificate, is refused with `CoreError::NewCertificate`, which carries both fingerprints. `Client::join_new_certificate` (the CLI's `socketchat join --new-certificate`, or Y in the chat screen's confirm box) connects under the link's certificate on a connection of its own and changes the pin only after that connection and the redeem both succeed.

The token works once and expires after `invite_ttl_hours`. A lodged request waits up to 7 days. A group invite can also register a server account for the joiner when the server allows members to invite.

## Files

`files.rs` seals a file in 64 KiB chunks with XChaCha20-Poly1305 STREAM, under a fresh random key and nonce prefix, while hashing the plaintext with SHA-256. JPEG, PNG, WebP and GIF images are first rewritten with only what draws the picture (`strip_image`), and a JPEG keeps only its orientation tag; files are recognized by their first bytes, not their names. Videos, photo formats the cleaner does not handle (`Kind::OtherPhoto`), and photos over 100 MiB or that the cleaner refuses need an explicit yes (`CoreError::PhotoNeedsConfirm`). The app uploads chunks in order (`FileBegin`, `FileChunk`, `FileEnd`), then sends a `FileOffer` with the key, nonce prefix, name, size and hash inside the group. Saving downloads chunk by chunk to a new part file (`create_part`: a random name, created only if nothing has that name, 0600 on Unix), checks the hash, and hard-links the result under a name that never replaces an existing file. `safe_name` keeps a saved name from starting with a dot or naming a Windows device, and the TUI's `pick_file` chooses among files that share a name. On drives without hard links, such as FAT32 and exFAT, it copies the result into a new file under such a name instead. Memory use stays flat however large the file is.

The server stores chunks as files under `files/` in its data directory and deletes a file once every member except the sender has reported `FileDone`, or at retention.

## Rooms that end

A room ends for a person when they leave it, an admin removes them, or it closes (`Ended::Left`, `Ended::Removed`, `Ended::Closed`). `Client::end_room` first writes an `ended_rooms` row with the room's name, kind, the reason, the time and the seen mark. From then on the room counts as ended, and if a later step fails, the next `Client::open` finishes the job. Then `Store::end_room` deletes, in one transaction, the room's rows in every `ROOM_STATE_TABLES` table (members, vouchers, files, owed proofs, expected joiners, close votes, kept closes, owed reposts, held profiles, its topic and invite links made into it), everything OpenMLS holds for the group, and the `groups` row with this member's group key. Before it deletes, it copies into `ended_names` the names of the people whose lines are still stored, so those lines keep their senders.

The room's history (`ROOM_HISTORY_TABLES`: `messages`, `extensions` and `ended_names`) stays until it is read. Each room keeps a seen mark, `groups.seen_seq`: a line counts as seen once the chat screen has shown its room, once this person sends in that room, or once `socketchat log` prints it. The CLI marks lines seen only up to the newest one it printed. `purge_read(keep)` deletes every ended room with nothing unseen except `keep`, the room on screen, and every room that ended at least `KEEP_UNSEEN_SECS` (30 days) ago. The chat screen calls it when another room opens and when it quits, and the CLI's commands call it before they finish. After this person's own leave with nothing unseen, `end_room` deletes the history at once.

Each deletion ends with `Store::checkpoint`, a `wal_checkpoint(TRUNCATE)` that clears old copies of the deleted rows out of SQLite's write-ahead log. When the log stays busy through three tries, the deletion still counts as done and the client warns.

A joiner lodges one KeyPackage per allowed suite. OpenMLS deletes the one a Welcome uses, and the client deletes the others with their private keys; `pending_joins.key_package_refs` remembers which they are.

## Closing a room

`close.rs` holds the rules and the tally, with no I/O. `close_needed` gives how many admins must agree: every admin when the room has up to 3, `n / 2 + 1` of `n` above that. `requests` counts each admin's newest vote, from the admins still in the room only.

`vote_close(gid, yes)` posts a `CloseVote`. The first yes starts a request with a random 16-byte ID, and the request stays open for `CLOSE_ASK_SECS` (7 days) from its first vote. A request that can no longer pass is kept, and `close_kept` remembers that, so it stays kept even when admins change later. The admin whose vote passes a request finishes the close at once, inside `vote_close`: it posts `Closed`, removes everyone else with one Commit, sends `LastLeave` so the server deletes the room, and ends the room as `Ended::Closed`. Another admin whose yes is in the count finishes it the same way during `sync` only when it finds the request passed and no `Closed` has arrived, as after the first admin's app stopped part way. Racing Commits resolve through the server's epoch check, so a close never waits on one app. Other members end the room as closed when they see `Closed` from an admin whose request passed, or when that admin's Commit removes them; `groups.closing` remembers a `Closed` that arrived first. `close_state` gives the request to show, as a `CloseView`.

## Invite lists

`invites_made` records each invite link this app makes: its token, server, room and expiry. `Client::invites` asks each server on protocol 2 for the open links (`ListInvites`). The server finds room links by their maker's keys, but keeps no record of who made a server link, so the app names its own by token, at most 100 per request. A link the server no longer lists was used, has expired or was cancelled, and the app forgets it. A server it cannot reach, or one on protocol 1, is skipped with a warning. `cancel_invite` sends `CancelInvite` and forgets the link.

## Storage

**Client.** One SQLite file, `socketchat.db`, encrypted with SQLCipher. The key comes from the passphrase through Argon2id (64 MiB, 3 passes, 4 lanes for new profiles since 0.5.1; 19 MiB, 2 passes, 1 lane before) with a random salt in a file beside it. That file starts with `sckdf` and a version byte 1, then the memory in KiB, passes and lanes as big-endian 32-bit numbers, then the 16-byte salt; a bare 16-byte salt from an older profile means 19 MiB, 2 passes and 1 lane. New settings in the same layout keep version 1, which every release reads; only a new layout would get a new version byte. A file that asks for more than 256 MiB of memory, 16 passes or 8 lanes, or for less than 8 KiB of memory per lane, is refused with "the profile's salt file is damaged" before any hashing starts, so a changed file cannot hang the app or run a 512 MB Raspberry Pi Zero 2 W out of memory. While the profile is open, the app holds an operating-system lock on a `lock` file beside it, so a second app on the same profile stops with "Socketchat is already open on this profile." Socketchat's own tables (profile, servers, groups, members, trusted identities, messages, vouchers, files, pending joins, invite proofs still owed) and OpenMLS's group state share that one connection, which `openmls_sqlite_storage` accepts. The profile lives in the platform's data folder, or in `SOCKETCHAT_HOME` if set. On Unix the folder is made 0700 and its files 0600, and a folder that another account owns is refused (`perms.rs`). A folder reached through a symbolic link is checked where it points: the owner check and the mode change go through one handle on the folder. A looser folder or file is narrowed when the profile opens, as best effort: a mode that cannot change (FAT, exFAT, some network shares) becomes a warning, and `Client::open_notes` holds one line saying what changed and one per failure, which the CLI prints. Profile files are narrowed through handles opened with `O_NOFOLLOW`, so a link among them is left alone. The salt file is read with `O_NOFOLLOW`, at most 35 bytes, and only as a plain file. `Store::create` makes the empty database file first, then the salt file, then derives the key. The salt file is written as `salt.new` (0600, never through a link), synced, renamed to `salt`, and the folder synced, so `salt` is either missing or whole after a power cut; a leftover `salt.new` is moved aside with the rest. With this order, a create stopped at any point leaves an empty database alone or beside its salt file. An empty database beside a salt file is a profile whose making stopped part way: `has_profile` says no and no passphrase opens it. `Store::create` checks that the salt file is in Socketchat's format, renames it, then the side files, then the database, to `<name>.unfinished-<unix time>`, and says so in `open_notes`; stopped part way, that too leaves an empty database with or without its salt file. It never deletes them. A salt file without a database may be waiting for it (a restore, a sync, a database moved aside), and a file named `salt` in another format belongs to someone else; `Store::create` refuses both and leaves them as they are. A database without its salt file gets a message that the salt file is missing.

Socketchat 0.5.0 adds these tables:

| Table | What it holds |
|---|---|
| `extensions` | Messages for add-ons and other programs: room, sequence number, sender, namespace, kind, version, body, summary and time. |
| `invites_made` | Invite links this app made: token, server, room (none for a server link) and expiry. |
| `ended_rooms` | Rooms this person is no longer in whose history is still here: name, kind, why it ended, when, and the seen mark. |
| `ended_names` | Names of the people whose lines are still stored for an ended room. |
| `close_votes` | Each admin's votes on closing a room: request ID, voter, yes or no, and when this app got it. |
| `close_kept` | Requests to close that this app saw end without closing. |

It also adds columns through `ADDED_COLUMNS`: `members.app_version` (the version a member said they run), `groups.announced_version` (the version this app last told the room), `groups.seen_seq` (the seen mark), `groups.muted`, `groups.closing` (a `Closed` this app knows of in the room, its own included while it closes the room) and `pending_joins.key_package_refs` (the KeyPackages lodged with a join request). On a profile from 0.4.0, every room starts with all of its history marked seen. `secure_delete` is on, so SQLite overwrites deleted rows inside the encrypted file.

**Server.** One SQLite file, `server.db`, in WAL mode, unencrypted because it holds nothing readable: accounts, invites, mailboxes, groups, the group log, join requests, Welcomes, file metadata and file receipts, plus OpenMLS's PublicGroup state. WAL mode lets `socketchat server invite` add an invite while the server runs. Secure delete is on, so SQLite overwrites deleted rows and cleared fields with zeros instead of leaving them in free pages. The hourly sweep in `retention.rs` deletes expired log entries, Welcomes, files, invites, join requests and unfinished mailboxes, and every group with no joined member. A log entry also goes once every member has acknowledged it. `delete_group` in `groups.rs` deletes a group and everything held for it in one transaction, for `LastLeave` and for the sweep, then removes its file chunks from disk. After a deletion, `db::checkpoint` clears old copies of the deleted rows out of the write-ahead log. `quota.rs` holds the storage limits and the count of accounts made through room links, and `perms.rs` makes the data directory 0700 and its files 0600, narrowing wider ones when the server starts. A Commit is checked in three steps (`post_commit` in `groups.rs`): the server reads the group under the database lock, runs OpenMLS's checks without it, and writes the Commit only if the epoch and the queued proposals are still what it read, answering `Conflict` otherwise, so a slow check never holds up other requests.
